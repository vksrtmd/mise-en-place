# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

Every comment or issue posted to the tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

Reference: [AGENT-BRIEF.md](AGENT-BRIEF.md) (durable agent briefs), [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) (the `.out-of-scope/` knowledge base).

## Roles

Each role is a label of the same name (the tracker doc says how to create a missing one).

Two **category** roles: `bug` (something is broken), `enhancement` (new feature or improvement).

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

Every triaged issue carries exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer first.

Transitions: an unlabeled issue goes to `needs-triage` first, then to `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag unusual transitions and ask before proceeding.

## Invocation

The maintainer invokes `/triage-tickets` and describes what they want ("show me anything that needs my attention", "let's look at #42", "move #42 to ready-for-agent", "triage these five bugs"). Interpret and act; more than one issue goes to [Several issues](#several-issues).

## Show what needs attention

Query the tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue

1. **Gather context.** Read the full issue (body, comments, labels, author, dates). Parse prior triage notes so you don't re-ask resolved questions. Explore the codebase with the domain glossary, respecting ADRs. Run two checks: (a) **redundancy**: search for an existing implementation by domain concept (not just the request's wording) and report where you looked; if found, it's an already-implemented `wontfix` (step 5). (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Give the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim** before any discussion. For a bug, reproduce it from the reporter's steps. Report confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal); a confirmed verification makes a much stronger brief. Do all checkouts, throwaway tests and installs in a scratch worktree. A batch agent uses the worktree its brief names; inline, make one on a branch `<issue number>-triage` per your branch and worktree rules, and remove it once the outcome is applied.

4. **Discuss (if needed).** When the request needs fleshing out, call the Skill tool with "discuss".

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: same structure, plus why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes ([template](#needs-info-template)).
   - `wontfix`: close, with the comment depending on *why*:
     - **Already implemented**: point to where it lives; write nothing to `.out-of-scope/` (that KB is for *rejected* requests).
     - **Rejected (bug)**: polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role; comment optional, e.g. for partial progress.

## Several issues

When given more than one issue, run them in parallel: one Sonnet subagent (`model: "sonnet"`) per issue or group, while you brief, check and ask.

1. **Group.** Read each issue. Issues sharing a code path, symptom or likely root cause go to one agent, so agents don't reproduce the same bug or post clashing briefs. Run as many at once as `~/.claude/docs/track-builds.md` step 4 allows.
2. **One worktree per agent**, made by you: a scratch branch from origin's default branch named `<lowest issue number in the group>-triage`, its path exactly as `git worktree list` prints it. The agent writes reproduction tests and runs installs there, and commits nothing.
3. **Brief each agent** with:
   - its issue numbers, this file's path, [AGENT-BRIEF.md](AGENT-BRIEF.md) and the tracker doc;
   - steps 1, 3 and 5 of [Triage a specific issue](#triage-a-specific-issue), in its worktree; the rules below replace step 2's "wait for direction" and step 5's `wontfix` bullet, and it applies the outcome itself;
   - before reporting, delete every file it created and name each tracked file it changed (a lockfile from an install, say);
   - the decision rules:
     - **Reproduced, and the fix can be stated as behavior with testable acceptance criteria**: post an agent brief, set the category role and `ready-for-agent`.
     - **Needs a judgment call, external access, a design decision or manual testing**: post the brief with why it can't be delegated, set `ready-for-human`.
     - **A question only the maintainer can answer decides the outcome** (intended behavior, which of two fixes): change nothing on that issue; hand the question back with its options and a recommendation.
     - **Any `wontfix`**: change nothing on that issue; hand it back as a question with a recommendation. The maintainer's answer decides the close and any `.out-of-scope/` entry.
     - **Can't reproduce**: post the [needs-info template](#needs-info-template), listing under "established so far" what was tried and on what setup, set `needs-info`.
     - **Finds a separate bug or follow-up**: files it as a new issue itself, with the disclaimer and these rules' roles, and links it from the triaged issue.
   - the disclaimer on every comment and new issue;
   - the wait block of `~/.claude/docs/track-builds.md` step 3, copied in;
   - its report, per issue: roles set, the comment's URL, each issue filed, each open question with options.
4. **Re-check each label on GitHub.** When an agent reports, read each issue it triaged or filed (`gh issue view <n> --json labels,comments`): exactly one category and one state role, matching the report, comment present with the disclaimer. Fix a mismatch yourself or resume the agent with SendMessage; a report is not proof of the label.
5. **Ask once.** Hold every question until all agents have reported, then ask together in one AskUserQuestion call (up to 4 questions; more in a second call right after). Apply each answer: set the role and post the comment yourself, or resume the owning agent with SendMessage.
6. **Clean up.** TaskStop each agent once its issues are settled, then remove its worktree and branch per your cleanup rule.
7. **Report** one line per issue: number, title, roles set, any issue filed from it.

## Quick state override

On "move #42 to ready-for-agent", trust the maintainer and apply the role directly: confirm what you're about to do (role changes, comment, close), then act, skipping discussion. When moving to `ready-for-agent` without a brief, ask whether they want one.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

Put everything resolved during the discussion under "established so far". Questions are specific and actionable, not "please provide more info".

## Resuming a previous session

When prior triage notes exist, read them, check whether the reporter answered any outstanding questions, and present an updated picture before continuing.
